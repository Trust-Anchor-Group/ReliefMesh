# Neuro authentication and onboarding investigation

This investigation was read-only except for temporary local runtime data, which was removed afterward. No OAuth client, Neuro/XMPP account, or Legal Identity was created. No credential or personal-information form was submitted.

## Separate security layers

These are different objects and must not be treated as one session:

1. **ReliefMesh application session**: product login and user state. The current loopback demo has no product user authentication.
2. **MCP session**: protocol session between ReliefMesh and an MCP server. Local STDIO uses Neuro-Ali's synthetic trusted user `STDIO`; hosted HTTP MCP requires separate HTTP authentication.
3. **Neuro/XMPP account**: the account and XMPP connection Neuro-Ali uses below MCP to reach the Neuron network.
4. **Legal Identity**: an identity application belonging to the authenticated Neuro/XMPP context, with its own lifecycle state.

## Reproduced local flow

1. A fresh Neuro-Ali data directory starts successfully and `tools/list` returns 68 tools before XMPP credentials exist.
2. The first Identity operation requiring an XMPP client triggers onboarding. This was reproduced with the read-only `GetIdentityApplicationProperties` tool.
3. Neuro-Ali sends MCP `elicitation/create` in URL mode. The URL has the form `http://localhost:<Neuro-Ali-port>/MCP/<elicitationId>`; the isolated reproduction used port 52500.
4. The page is generated by the local Neuro-Ali HTTP server. It is MCP URL elicitation, not an OAuth authorization redirect and not a page hosted by `lab.tagroot.io`.
5. The form displays Domain, User Name, Password, Trust Server, Allow Insecure Mechanisms, Create Account, API Key, and API Secret. It posts to the same one-time localhost URL with signed hidden parameters.
6. On an accepted POST, Neuro-Ali validates the one-time request, copies submitted values into the pending input object, reports the elicitation result, emits `notifications/elicitation/complete`, and resumes the original tool call.
7. With valid existing-account credentials, Neuro-Ali opens an XMPP connection and stores reusable connection credentials in its encrypted database. Historical execution confirms that the original identity tool then completes in the same MCP session.

The visible **Create Account** control does not currently work. In installed `Waher.Mcp.Xmpp` 1.0.2, `CreateAccount`, `ApiKey`, and `ApiSecret` are declared on the input model but are never consumed by `XmppMcpServer`. It constructs a normal login client and does not enable XMPP registration. The form therefore supports existing-account login only in the currently installed package.

## Hosted MCP authentication

The hosted Identity endpoint is `https://lab.tagroot.io/MCP/Identity` and negotiates MCP protocol `2025-11-25`. Initialization is available without credentials, but `tools/list` and Identity tool calls return HTTP 401 until the MCP client authenticates.

The 401 challenge advertises Bearer, Basic, and Digest authentication. Standard discovery confirms a real OAuth 2 surface:

- Protected-resource metadata: `https://lab.tagroot.io/.well-known/oauth-protected-resource/MCP/Identity`
- Authorization-server metadata: `https://lab.tagroot.io/.well-known/oauth-authorization-server`
- Authorization endpoint: `https://lab.tagroot.io/oauth/authorize`
- Token endpoint: `https://lab.tagroot.io/oauth/token`
- Dynamic client registration: `https://lab.tagroot.io/oauth/register`
- Identity scopes: `MCP:Identity:Tools`, `MCP:Identity:Prompts`, and `MCP:Identity:Resources`
- Advertised grants include authorization code and refresh token

A read-only authorization request rendered the hosted OAuth **Login** page and warned that the test client was unregistered. This proves the hosted browser authorization surface exists. It does not prove a successful callback, which user account authenticates there, whether that account is the same as an XMPP account, or whether end-user self-registration is available. Dynamic OAuth client registration creates an application client, not a human Neuro account; it was not invoked.

## Controlled OAuth certification attempt

On 2026-09-07, one dynamic client registration request was sent to the advertised endpoint. The request used the implementation's exact RFC 7591 fields: a literal `http://localhost:53682/oauth/callback` redirect, authorization-code and refresh-token grants, code response type, `client_secret_basic`, and the advertised Identity, XMPP, and Payments MCP scopes. Literal `localhost` was required because this server implementation does not apply its insecure-loopback exception to `127.0.0.1`.

Lab returned HTTP 403 with `access_denied` and `Not permitted to register new client.` No client ID, client secret, registration access token, authorization request, login, callback, authorization code, access token, or refresh token was created. The test stopped at that operator policy boundary; registration was not retried and no OAuth harness was started.

```ini
OAUTH_DYNAMIC_REGISTRATION=FAIL
CLIENT_TYPE=confidential (requested; not registered)
REDIRECT_URI=http://localhost:53682/oauth/callback
AUTHORIZATION_ENDPOINT=https://lab.tagroot.io/oauth/authorize
TOKEN_ENDPOINT=https://lab.tagroot.io/oauth/token
HOSTED_OAUTH_LOGIN=NOT_RUN
HOSTED_OAUTH_CALLBACK=NOT_RUN
ACCESS_TOKEN_RECEIVED=NO
HOSTED_MCP_INITIALIZE=NOT_RUN_WITH_TOKEN
HOSTED_MCP_TOOLS_LIST=NOT_RUN_WITH_TOKEN
HOSTED_MCP_IDENTITY_READ=NOT_RUN_WITH_TOKEN
```

The advertised OAuth server supports S256 PKCE, authorization codes, refresh tokens, and confidential client authentication. Those are protocol capabilities, not a successful ReliefMesh authorization. An operator must provision a client or grant ReliefMesh permission to register one before end-to-end certification can continue.

## Answers to the onboarding questions

1. **Trigger:** the first XMPP-dependent tool call with no persisted credentials. `GetIdentityApplicationProperties` is a safe reproducible trigger.
2. **URL and protocol:** local onboarding is HTTP on `http://localhost:<port>/MCP/<elicitationId>`. Hosted MCP is HTTPS at `https://lab.tagroot.io/MCP/Identity`.
3. **OAuth or elicitation:** the localhost page is MCP URL elicitation carrying XMPP credentials. Hosted HTTP MCP separately supports OAuth 2 and direct HTTP authentication.
4. **Create Account control:** yes, it is visibly rendered on the local form.
5. **What it creates:** it is labelled as XMPP account creation, but the installed package ignores it and creates no account.
6. **Successful existing-account login:** it opens the XMPP connection, caches the client in memory, persists reusable hashed credentials, and resumes the original MCP tool.
7. **Local callback:** POST to the same one-time localhost URL. There is no browser redirect to Lab in this flow. Hosted OAuth would use a registered client redirect URI, but that callback was not exercised.
8. **Completion:** the POST resolves the pending request, triggers `notifications/elicitation/complete`, and lets the original tool return.
9. **Resulting credentials:** local flow retains the XMPP account/domain and password hash plus hash method. The MCP session ID remains in memory. No local OAuth access or refresh token is issued.
10. **Storage:** XMPP credentials are encrypted in `McpXmppClientCredentials` inside the Neuro-Ali data directory and keyed by MCP user name. ReliefMesh stores only its own ignored onboarding flags. Hosted token storage is not implemented.
11. **Tool visibility:** local STDIO listed 68 tools before XMPP login. Hosted HTTP `tools/list` requires HTTP authentication.
12. **Application properties:** after valid XMPP login, the same local session can call `GetIdentityApplicationProperties`; this was previously completed successfully.
13. **Identity application:** the same context can call `ApplyForNewPersonalIdentity`; this is a non-idempotent mutation and starts a second sensitive elicitation.
14. **Existing identity detection:** call authenticated `resources/list`, select Identity resources, and inspect/read their state. Only `State == "Approved"` establishes approved identity readiness. Application-property discovery does not.
15. **Lab account creation:** not established. The current local MCP control is unwired, and hosted OAuth discovery says nothing about human account self-registration. Lab operator registration policy or a package fix/upgrade is required before claiming signup support.
16. **Approval:** `ReadyForApproval` submits the application for Trust Provider review. The observed Lab workflow required manual administrator approval. Source supports automatic approval, rejection, peer review, or manual review in principle, so manual review is observed Lab behavior rather than a protocol invariant.

## Architecture decision

**Option A remains the preferred product target, but is not end-to-end certified.** Lab exposes a standards-based hosted OAuth authorization server and protected HTTP MCP endpoint, but anonymous dynamic client registration is forbidden. Before implementation, obtain an operator-provisioned ReliefMesh OAuth client or explicit registration permission, then validate authorization-code callback, PKCE, token refresh/revocation, account mapping, logout, and end-user provisioning.

**Option B is the only currently demonstrated end-to-end ReliefMesh integration.** It requires one isolated Neuro-Ali process, MCP session, port, and encrypted data directory per ReliefMesh user. Sharing the current local process is unsafe because STDIO always authenticates as `STDIO` and persisted XMPP credentials are keyed by that single MCP user name. Option B also cannot provide product signup until XMPP registration is fixed or upgraded.

Do not implement a generic `Continue with Neuro` button as though the localhost elicitation were OAuth. Implement hosted OAuth only after the remaining Lab contract is validated; otherwise use isolated per-user Neuro-Ali instances as the explicit fallback.

```ini
HOSTED_OAUTH_CERTIFIED=NO
MULTI_USER_HOSTED_MCP_FEASIBLE=NOT_YET_PROVEN
PER_USER_NEUROALI_REQUIRED=YES_FOR_CURRENTLY_PROVEN_ARCHITECTURE
RECOMMENDED_PRODUCT_ARCHITECTURE=Hosted per-user OAuth MCP after operator client provisioning and end-to-end certification
BLOCKERS=Lab denied dynamic client registration; no registered client means login, callback, token, user binding, service coverage, refresh behavior, and hosted elicitation remain uncertified
```
